== Learning objectives

By the end of this module, you'll be able to:

* Read a Praxis configuration and explain the pipeline each listener builds
* Route requests by path and header, and balance them with round-robin and weighted strategies
* Protect backends with a rate limit and active health checks
* Change configuration live from a ConfigMap and confirm that invalid changes are rejected

== Deploy the Praxis gateway

The gateway is five pieces: the Praxis configuration, the Praxis pod, a Service, a Route per listener and a ServiceMonitor for metrics.

. Create the ConfigMap that holds the Praxis configuration. It defines two listeners, the filter chains they run and the backend clusters; you read it in detail in Exercise 1:
+
[source,role="execute"]
----
cat << 'EOF' | oc apply -f -
include::example$06-basics-configmap.yaml[]
EOF
----
+
Two parts of that configuration to notice first.
+
A **listener** is an address Praxis accepts connections on, and the list of filter chains to run for each request it receives:
+
[source,yaml]
----
listeners:
  - name: web
    address: "0.0.0.0:8080"
    filter_chains: [observability, edge, routing]
----
+
`web` listens on port 8080 on all interfaces, so the Service and Route can reach it. Every request runs the `observability`, `edge` and `routing` chains, in that order. Each chain is defined further down under `filter_chains`.
+
A **cluster** is a named group of backends that requests can be sent to:
+
[source,yaml]
----
clusters:
  - name: app
    endpoints:
      - "backend-a.praxis.svc.cluster.local:8080"
      - "backend-b.praxis.svc.cluster.local:8080"
----
+
The `app` cluster holds two echo servers, addressed by their Service DNS names. The `router` filter sends requests to a cluster by name, and the `load_balancer` filter picks one endpoint in it. The full entry also defines a health check for these endpoints, which you use in Exercise 5.

----

== Exercise 1: Listeners, filter chains and pipelines

Start by reading the configuration you just deployed.

. Print the configuration:
+
[source,role="execute"]
----
oc get cm praxis-basics-config -o jsonpath='{.data.praxis\.yaml}'
----

. Find the `listeners` and `filter_chains` sections. The two listeners use the same chains, and `limited` adds one:
+
[source,yaml]
----
listeners:
  - name: web
    address: "0.0.0.0:8080"
    filter_chains: [observability, edge, routing]
  - name: limited
    address: "0.0.0.0:8081"
    filter_chains: [observability, throttle, edge, routing]
----
+
At startup Praxis joins each listener's chains, in order, into one pipeline:
+
----
listener web:     [observability] + [edge] + [routing]
  -> request_id, access_log, headers, static_response, router, load_balancer

listener limited: [observability] + [throttle] + [edge] + [routing]
  -> request_id, access_log, rate_limit, headers, static_response, router, load_balancer
----
+
The two listeners differ by one chain name, and no filter configuration is duplicated. Each listener gets its own copy of the filters, so stateful filters such as a rate limiter keep separate state per listener.

. See a filter answer a request on its own. The `static_response` filter has a condition, `when: path: "/"`, so it answers only `/`:
+
[source,role="execute"]
----
curl -i $B/
----

. Request a path with no matching route:
+
[source,role="execute"]
----
curl -i $B/nope
----

=== Verify

Expected output from `curl -i $B/` (headers trimmed):

----
HTTP/1.1 200 OK
content-type: application/json

{"lab": "praxis", "try": ["/app", "/canary", "/v2"]}
----

Expected first line from `curl -i $B/nope`:

----
HTTP/1.1 404 Not Found
----

* `/` is answered by `static_response`, so the router and load balancer never run and no backend is contacted
* `/nope` passes `static_response` (its condition doesn't match) and reaches the router, which finds no route and returns 404

== Exercise 2: Routing on path and headers

The `router` filter picks a cluster for each request by comparing it with a list of routes. Each route has a `path_prefix`, and can also require a host or particular headers.

**When does a prefix match?** The request path must start with the prefix at a `/` boundary. The prefix `/app` matches `/app` and `/app/hello`, but not `/application`.

**What if several routes match?** Praxis picks the most specific one:

* **The longer prefix wins.** Suppose there were routes for `/` and for `/api`. A request for `/api/users` matches both, and `/api` wins because it's longer. The `/` route then only catches requests that nothing more specific matches.
* **On a tie, the route with more conditions wins.** If two matching routes have the same prefix, the one that also requires a host or headers is more specific.

The order of the routes in the file doesn't matter.

. Request `/app`, which routes to the `app` cluster (backend-a and backend-b), then `/application`, which the `/app` prefix doesn't match:
+
[source,role="execute"]
----
curl -s $B/app | grep Name
curl -s -o /dev/null -w '%{http_code}\n' $B/application
----

. Request `/v2` twice without the `x-version: v2` header, then once with it:
+
[source,role="execute"]
----
for i in 1 2; do curl -s $B/v2 | grep Name; done
curl -s -H 'x-version: v2' $B/v2 | grep Name
----
+
Two routes share the `/v2` prefix, so the tie rule applies. With the header, both routes match and the one that requires `x-version: v2` wins because it's more specific. Without the header, only the plain `/v2` route matches, so the request goes to the `app` cluster:
+
[source,yaml]
----
- path_prefix: "/v2"
  cluster: v2
  headers:
    x-version: v2
- path_prefix: "/v2"
  cluster: app
----
+
Without the header, the reply alternates between backend-a and backend-b. Routing and load balancing are two separate decisions. The `router` picks the `app` cluster, and `app` has two endpoints, backend-a and backend-b. The `load_balancer` then picks one of them, and its default strategy is round robin, so each request goes to the next endpoint in turn. Which one answers first depends on how many requests the `web` listener has already sent to `app`, including the `/app` request in the previous step. With the header, the router picks the `v2` cluster, which has only backend-c, so the answer is always the same.

=== Verify

Expected output for `/app` and `/application` (the first line can be backend-a or backend-b):

----
Name: backend-a
404
----

Expected output for the three `/v2` requests (the first two can come in either order):

----
Name: backend-b
Name: backend-a
Name: backend-c
----

* `/application` gets a 404: it starts with the letters `/app` but not the path segment `/app`, so no route matches
* Without the header, `/v2` goes to the `app` cluster, and round robin alternates between backend-a and backend-b
* With `x-version: v2`, it goes to backend-c

== Exercise 3: Load balancing and header changes

The `load_balancer` filter picks an endpoint inside the chosen cluster.

. Send four requests to `/app`:
+
[source,role="execute"]
----
for i in 1 2 3 4; do curl -s $B/app | grep Name; done
----

. Send twenty requests to `/canary` and count where they went:
+
[source,role="execute"]
----
for i in $(seq 1 20); do curl -s $B/canary | grep Name; done | sort | uniq -c
----
+
The `canary` cluster weights its endpoints 3 and 1:
+
[source,yaml]
----
- name: canary
  load_balancer_strategy: round_robin
  endpoints:
    - address: "backend-a.praxis.svc.cluster.local:8080"
      weight: 3
    - address: "backend-c.praxis.svc.cluster.local:8080"
      weight: 1
----
+
Other strategies include least connections, consistent hashing, power of two choices and zone-aware balancing.

. Look at the full request the backend received:
+
[source,role="execute"]
----
curl -s $B/app/hello
----

. Look at the response headers Praxis added:
+
[source,role="execute"]
----
curl -si $B/app | grep -i -E 'x-powered-by|x-request-id'
----

=== Verify

Expected output for `/app` and `/canary`:

----
Name: backend-a
Name: backend-b
Name: backend-a
Name: backend-b

     15 Name: backend-a
      5 Name: backend-c
----

Expected lines in the echoed request:

----
Via: 1.1 praxis
X-Request-Id: 5f65ba4c192224e89c71000000000006
X-Via: praxis-lab
----

* `/app` alternates between backend-a and backend-b
* `/canary` gives exactly 15 and 5: weighted round robin is deterministic
* The `headers` filter added `X-Via`, `request_id` added `X-Request-Id`, and Praxis added `Via`
* The response carries `x-powered-by: praxis` and the same `X-Request-Id`

The echo also shows `Forwarded` and `X-Forwarded-*` headers. Those come from the OpenShift router, a second proxy in front of Praxis.

Each `load_balancer` cluster lists its backends' DNS names in `trusted_private_endpoints`. Service names resolve to private cluster IPs, and without that allowlist Praxis refuses to connect to them.

== Exercise 4: Rate limiting

The rate limit is a filter chain of its own, `throttle`, containing one `rate_limit` filter:

[source,yaml]
----
filter_chains:
  - name: throttle
    filters:
      - filter: rate_limit
        mode: global
        rate: 2
        burst: 4
----

The `rate_limit` filter is a **token bucket**. Each request takes one token from the bucket, and a request that finds the bucket empty is rejected with 429.

* `burst: 4` is the bucket's size: up to 4 requests can go through back to back.
* `rate: 2` is how fast it refills: 2 tokens per second, so the sustained limit is 2 requests per second.
* `mode: global` means one bucket shared by every client. With `mode: per_ip`, each client IP address gets its own bucket instead.

Only one of the two listeners includes the `throttle` chain:

[source,yaml]
----
listeners:
  - name: web
    address: "0.0.0.0:8080"
    filter_chains: [observability, edge, routing]
  - name: limited
    address: "0.0.0.0:8081"
    filter_chains: [observability, throttle, edge, routing]
----

Requests to the `limited` listener, on port 8081, pass through `rate_limit` before routing. Requests to `web` never meet it. Each listener has its own Route, so `$L` reaches `limited` and `$B` reaches `web`.

. Send ten quick requests through the limited Route:
+
[source,role="execute"]
----
for i in $(seq 1 10); do curl -s -o /dev/null -w '%{http_code} ' $L/app; done; echo
----

. Look at the headers on a rejected request:
+
[source,role="execute"]
----
curl -si $L/app | grep -i -E '^HTTP|ratelimit|retry-after'
----

. Send the same ten requests through the `web` Route:
+
[source,role="execute"]
----
for i in $(seq 1 10); do curl -s -o /dev/null -w '%{http_code} ' $B/app; done; echo
----

=== Verify

Expected output (the exact count before the first 429 varies):

----
200 200 200 200 200 200 429 429 429 429
HTTP/1.1 429 Too Many Requests
retry-after: 1
x-ratelimit-limit: 4
x-ratelimit-remaining: 0
200 200 200 200 200 200 200 200 200 200
----

* The limited Route returns 429 with `Retry-After` and `X-RateLimit-*` headers once the bucket is empty
* Usually 5 or 6 requests succeed, not 4, because the bucket refills while requests cross the network
* The `web` Route is never limited

Why a separate listener rather than a condition such as `when: path_prefix: /limited`? Praxis treats `rate_limit` as a security filter and refuses to start if a security filter has a condition, because a condition is a way around it. You can opt in under `insecure_options`, but a separate listener keeps the limit unconditional.

== Exercise 5: Health checks

The `app` cluster probes `GET /health` on each backend every 2 seconds and removes a backend that fails twice. whoami lets you change what its `/health` returns with a POST. The whoami image has no shell, so you send the POST from the Praxis pod, which has busybox `wget`.

. Make backend-a report itself unhealthy:
+
[source,role="execute"]
----
H=http://backend-a.praxis.svc.cluster.local:8080/health
oc exec deploy/praxis-basics -- wget -qO- --post-data=500 $H
sleep 5
----

. Check Praxis's readiness report and send some traffic:
+
[source,role="execute"]
----
oc exec deploy/praxis-basics -- wget -qO- http://127.0.0.1:9902/ready; echo
for i in 1 2 3 4; do curl -s $B/app | grep Name; done
----

. Make backend-a healthy again:
+
[source,role="execute"]
----
oc exec deploy/praxis-basics -- wget -qO- --post-data=200 $H
----

=== Verify

Expected output while backend-a is failing:

----
{"status":"ok","clusters":{"total":1,"healthy":1,"degraded":0,"detail":{"app":{"healthy":1,"unhealthy":1,"total":2}}}}
Name: backend-b
Name: backend-b
Name: backend-b
Name: backend-b
----

* `/ready` reports one healthy and one unhealthy endpoint in `app`
* All traffic goes to backend-b until backend-a recovers

`/ready` is also the Deployment's readiness probe, and `/healthy` its liveness probe, both on the metrics port 9902. `/ready` returns 503 when any cluster has no healthy endpoints, which takes the pod out of its Route. That suits this gateway, whose only job is the `app` cluster; Module 3 explains why the AI gateway uses `/healthy` instead.

== Exercise 6: Hot reload from the ConfigMap

Praxis watches its configuration file. When the file changes, it validates the new configuration, rebuilds the pipelines and swaps them in. In-flight requests finish on the old pipeline.

. Change the `X-Powered-By` response header from `praxis` to `praxis-reloaded`:
+
[source,role="execute"]
----
oc get cm praxis-basics-config -o yaml \
  | sed 's/value: praxis$/value: praxis-reloaded/' | oc apply -f -
----

. Wait for the change to take effect, then look at the reload in the log. The kubelet copies ConfigMap changes into the pod on its own schedule, usually within a minute, so the loop waits for the new header value itself:
+
[source,role="execute"]
----
until curl -si $B/app | grep -qi 'x-powered-by: praxis-reloaded'; do sleep 5; done
oc logs deploy/praxis-basics --since=3m | grep -i reload
----

. Check the header and the pod:
+
[source,role="execute"]
----
curl -si $B/app | grep -i x-powered-by
oc get pods -l app=praxis-basics
----

. Now break it: point the `/canary` route at a cluster that doesn't exist:
+
[source,role="execute"]
----
oc get cm praxis-basics-config -o yaml \
  | sed 's/cluster: canary$/cluster: does-not-exist/' | oc apply -f -
until oc logs deploy/praxis-basics --since=2m | grep -q 'reload failed'; do sleep 5; done
oc logs deploy/praxis-basics --since=2m | grep -i 'reload failed'
curl -s $B/canary | grep Name
----

. Restore the original configuration:
+
[source,role="execute"]
----
cat << 'EOF' | oc apply -f -
include::example$06-basics-configmap.yaml[]
EOF
----

=== Verify

Expected output after the first change:

----
x-powered-by: praxis-reloaded
NAME                             READY   STATUS    RESTARTS   AGE
praxis-basics-7d9c6b8f5d-k2x4p   1/1     Running   0          12m
----

Expected output after the broken change:

----
ERROR ... config reload failed error=pipeline validation failed for listener 'web': cluster-selecting filter references cluster 'does-not-exist' which is not defined in the load_balancer configuration
Name: backend-a
----

* The valid change went live with `RESTARTS` still `0`
* The invalid change was rejected, and `/canary` kept working on the old configuration

[TIP]
====
Mount the ConfigMap as a directory, not with `subPath`. Kubernetes only updates directory mounts, so a `subPath` mount never sees changes. Routes, filters, clusters and weights reload live; listener addresses, protocol and TLS on or off need a restart.
====

== Learning outcomes

By completing this module, you should now understand:

* ✓ How a listener's chains become one pipeline, and how filters short-circuit it
* ✓ How the router and load balancer split the decision of where a request goes
* ✓ Why Praxis refuses conditional security filters and unlisted private backends
* ✓ How hot reload swaps configuration safely, and what happens to an invalid change
