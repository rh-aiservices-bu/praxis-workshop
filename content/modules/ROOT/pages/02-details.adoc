== Technical requirements

=== Software versions

This workshop was tested with:

* Red Hat OpenShift {ocp_version}, on CPU-only worker nodes
* Red Hat OpenShift AI {rhoai_version}, with KServe model serving in its default RawDeployment mode
* Praxis core {praxis_version} (`ghcr.io/praxis-proxy/praxis`)
* Praxis AI {praxis_ai_version} (`ghcr.io/praxis-proxy/ai`)
* llm-d inference simulator {sim_version} (`ghcr.io/llm-d/llm-d-inference-sim`)
* traefik/whoami v1.10 (`docker.io/traefik/whoami`)

All images are published, so nothing is built during the workshop. The Praxis images are built for the amd64 (x86_64) architecture only.

=== Environment access

You need:

* **Red Hat OpenShift AI 3.x with KServe enabled.** The environment provides it; the workshop doesn't install it. KServe must be `Managed` in the DataScienceCluster.
* cluster-admin access, or a user who can create a project, ResourceQuota, ServingRuntime, InferenceService and ServiceMonitor
* Outbound access from the cluster to `ghcr.io` and `docker.io` to pull images
* User workload monitoring enabled, for the metrics steps in the OpenShift console
* The Cluster Observability Operator, with Perses enabled in its monitoring console plugin, for the dashboard in Module 2 Exercise 7. Without it, everything else still works.

=== GPU guardrails

The workshop never uses a GPU, even on a GPU node:

* A ResourceQuota named `no-gpus` in the `{namespace}` project forbids requesting any GPU.
* Every container the workshop defines sets `NVIDIA_VISIBLE_DEVICES=void`, so the NVIDIA container runtime never hands it a GPU. That includes the model containers, through the simulator's ServingRuntime.
* All pods run under OpenShift's default `restricted-v2` security context: a random non-root UID, a read-only root filesystem and no Linux capabilities.

== Using the terminal

Commands in this workshop run in the **Terminal** tab on the right. Click a command block to run it there.

Several steps set shell variables (such as `B` and `AI`) or define a small `chat` helper function. These last for the current terminal session. If the terminal reconnects, rerun the block that defines them; each module shows it near the top.

== Setup validation

Confirm that you're logged in to the cluster:

[source,role="execute"]
----
oc whoami
----

If you aren't logged in, log in with the cluster-admin credentials:

[source,role="execute",subs="attributes+"]
----
oc login -u {admin_user} -p {admin_password} {api_url}
----

Check that user workload monitoring is enabled:

[source,role="execute"]
----
oc get pods -n openshift-user-workload-monitoring
----

Expected output (pod names vary):

----
NAME                                   READY   STATUS    RESTARTS   AGE
prometheus-operator-5ff8fc6c68-dxqll   2/2     Running   0          2h
prometheus-user-workload-0             6/6     Running   0          2h
thanos-ruler-user-workload-0           4/4     Running   0          2h
----

If there are no pods, the workshop still works. Only the console metrics steps need user workload monitoring.

Check that OpenShift AI model serving (KServe) is available:

[source,role="execute"]
----
oc get crd inferenceservices.serving.kserve.io servingruntimes.serving.kserve.io
----

Expected output:

----
NAME                                  CREATED AT
inferenceservices.serving.kserve.io   2026-11-04T18:31:57Z
servingruntimes.serving.kserve.io     2026-11-04T18:32:00Z
----

If these resource types don't exist, OpenShift AI with KServe isn't installed, and Module 1 Exercise 2 and Module 3 can't run.

Check that Perses dashboards are available:

[source,role="execute"]
----
oc get crd persesdashboards.perses.dev persesdatasources.perses.dev
----

If these don't exist, skip the dashboard steps in Module 2 Exercise 7 and Module 3 Exercise 5.

== Troubleshooting

**Issue**: Pods stuck in `ImagePullBackOff`

**Solution**: The cluster can't reach `ghcr.io` or `docker.io`. Check with `oc -n {namespace} describe pod <pod-name>` and look at the events.

**Issue**: A Praxis pod is in `CrashLoopBackOff`

**Solution**: Praxis refuses to start with an invalid config and logs the reason. Run `oc -n {namespace} logs deploy/<name>` and read the last lines.

**Issue**: An InferenceService stays `READY False`

**Solution**: Run `oc -n {namespace} describe inferenceservice <name>` and `oc -n {namespace} get pods -l serving.kserve.io/inferenceservice=<name>`. The usual causes are an image pull problem or a missing ServingRuntime: the runtime `llm-d-inference-sim` must exist in the `{namespace}` project.

**Issue**: `forbidden: exceeded quota: no-gpus`

**Solution**: Something asked for a GPU. The quota is working as intended; remove the GPU request from that manifest.
