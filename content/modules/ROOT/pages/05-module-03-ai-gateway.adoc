Praxis AI {praxis_ai_version} is Praxis core plus filters that understand AI traffic. Everything from Module 2 still applies: the same listeners, chains, router, load balancer, health checks, hot reload and metrics. In this module you put it in front of the simulated models served by OpenShift AI and use what it adds.

== Learning objectives

By the end of this module, you'll be able to:

* Route OpenAI-compatible requests by the `model` field in the request body
* Balance and fail over between two InferenceServices that serve the same model
* Serve Anthropic Messages clients from OpenAI Chat Completions backends, including streaming
* Monitor token usage and time to first token per model

== Deploy the Praxis AI gateway

The gateway is five pieces, like the one in Module 2: the Praxis AI configuration, the Praxis AI pod, a Service, a Route and a ServiceMonitor. Its listener runs four chains:

* **`observability`**: `request_id` and `access_log`, as in Module 2
* **`classify`**: work out which AI API the request uses and which model it asks for
* **`translate`**: convert Anthropic Messages requests and responses to and from OpenAI Chat Completions
* **`routing`**: `router`, token accounting and `load_balancer`

. Create the ConfigMap that holds the Praxis AI configuration: the listener and its four chains, routes for the two models, a health check on each granite InferenceService, and a `load_balancer` cluster per model that points at its KServe predictor address, such as `granite-a-predictor.praxis.svc.cluster.local:8000`:

EOF

. Save the Route URL and define a small `chat` helper that sends an OpenAI Chat Completions request for a given model. Rerun this block if your terminal reconnects.
+
[source,role="execute"]
----
AI=https://$(oc get route praxis-ai -o jsonpath='{.spec.host}')
chat() {  # chat <model> [extra curl args...]
  local model=$1; shift
  curl -s "$AI/v1/chat/completions" -H 'content-type: application/json' "$@" \
    -d "{\"model\":\"$model\",\"max_tokens\":20,\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}]}"
}
echo "AI gateway: $AI"
----

[NOTE]
====
Unlike the Module 2 gateway, this Deployment's readiness probe uses `/healthy`, not `/ready`. `/ready` returns 503 when any cluster has no healthy endpoints, so with many models, one stopped model would take the whole gateway out of its Route. In Praxis {praxis_version}, `/ready` also keeps reporting the endpoints the pod started with after a hot reload. Use `/ready` to monitor backend health instead.
====

== Exercise 1: One endpoint, many models

All OpenAI clients call the same URL. Praxis picks the backend from the `model` field inside the JSON body.

. Ask each model a question:
+
[source,role="execute"]
----
chat granite-3.1-8b-instruct | head -c 200; echo
chat qwen3-8b | head -c 200; echo
----

. Ask for a model the gateway doesn't know:
+
[source,role="execute"]
----
chat gpt-4o -i | head -1
----

. Try to steer routing with a header:
+
[source,role="execute"]
----
chat granite-3.1-8b-instruct -H 'X-Model: qwen3-8b' -D - -o /dev/null | grep -i x-inference-pod
----

The routing happens in three steps:

* **`ai_operation`** identifies the AI API and operation (OpenAI Chat, Responses, Anthropic Messages and so on) from the method and path alone, before reading any body.
* **`model_to_header`** reads `model` from the body without forwarding anything yet, and copies it into the `X-Model` header. It **replaces** any client-sent `X-Model`.
* **`router`** matches `X-Model` to a cluster, exactly as in Module 2.

This is the **classify, promote, route** pattern: turn something in the request into a header, then route on the header.

=== Verify

Expected output (response bodies trimmed):

----
{"id":"chatcmpl-...","model":"granite-3.1-8b-instruct","object":"chat.completion",...
{"id":"chatcmpl-...","model":"qwen3-8b","object":"chat.completion",...
HTTP/1.1 404 Not Found
x-inference-pod: granite-b-predictor-6d8fd8fdbc-dplqd
----

* Each model answers its own requests
* An unknown model gets a 404, because no route matches it
* The request with `X-Model: qwen3-8b` still reached a granite pod: routing follows the body, not the client's header

== Exercise 2: Balancing and failover across InferenceServices

`granite-a` and `granite-b` are two InferenceServices serving the same model. Praxis lists both in its `granite` cluster, balances between them, and health-checks each one, so it can fail over when one stops. The simulator returns an `x-inference-pod` response header naming the pod that answered.

. Send four requests for granite and two for qwen:
+
[source,role="execute"]
----
for i in 1 2 3 4; do chat granite-3.1-8b-instruct -D - -o /dev/null | grep -i x-inference-pod; done
for i in 1 2; do chat qwen3-8b -D - -o /dev/null | grep -i x-inference-pod; done
----

. Stop `granite-b`. The `serving.kserve.io/stop` annotation is what the **Stop** action in the OpenShift AI dashboard sets: KServe removes the model's pod and keeps its definition.
+
[source,role="execute"]
----
oc annotate inferenceservice granite-b serving.kserve.io/stop=true --overwrite
sleep 10
oc get inferenceservice granite-b
----

. Check how many granite endpoints Praxis considers healthy, and send traffic. Read the metrics rather than `/ready`, which can be out of date after a hot reload (see the note under "Deploy the Praxis AI gateway"):
+
[source,role="execute"]
----
oc exec deploy/praxis-ai -- wget -qO- http://127.0.0.1:9902/metrics | grep '^praxis_upstream_healthy_endpoints'
for i in 1 2 3 4; do chat granite-3.1-8b-instruct -D - -o /dev/null | grep -i x-inference-pod; done
----

. Start `granite-b` again. Its new pod has a new IP address, and Praxis caches DNS answers for 60 seconds, so wait a minute before sending traffic:
+
[source,role="execute"]
----
oc annotate inferenceservice granite-b serving.kserve.io/stop=false --overwrite
oc wait --for=condition=Ready inferenceservice/granite-b --timeout=180s
sleep 60
oc exec deploy/praxis-ai -- wget -qO- http://127.0.0.1:9902/metrics | grep '^praxis_upstream_healthy_endpoints'
for i in 1 2 3 4; do chat granite-3.1-8b-instruct -D - -o /dev/null | grep -i x-inference-pod; done
----

. Errors from the model itself pass straight through. The simulator fails on demand when you send an `X-Return-Error` header:
+
[source,role="execute"]
----
chat qwen3-8b -H 'X-Return-Error: 429' -w '\n%{http_code}\n'
----

=== Verify

Expected output from the first step (pod names vary):

----

x-inference-pod: granite-b-predictor-6d8fd8fdbc-dplqd
x-inference-pod: granite-a-predictor-5895f7b954-9sltf
x-inference-pod: granite-b-predictor-6d8fd8fdbc-dplqd
x-inference-pod: qwen-predictor-996f876c8-vfp89
x-inference-pod: qwen-predictor-996f876c8-vfp89
----

Expected output while `granite-b` is stopped:

----
NAME        URL   READY   PREV   LATEST   PREVROLLEDOUTREVISION   LATESTREADYREVISION   AGE
granite-b         False                                                                 33m
praxis_upstream_healthy_endpoints{cluster="granite"} 1
x-inference-pod: granite-a-predictor-5895f7b954-9sltf
x-inference-pod: granite-a-predictor-5895f7b954-9sltf
x-inference-pod: granite-a-predictor-5895f7b954-9sltf
x-inference-pod: granite-a-predictor-5895f7b954-9sltf
----

Expected output after the restart:

----
praxis_upstream_healthy_endpoints{cluster="granite"} 2
x-inference-pod: granite-b-predictor-6d8fd8fdbc-pclhx
x-inference-pod: granite-a-predictor-5895f7b954-9sltf
x-inference-pod: granite-b-predictor-6d8fd8fdbc-pclhx
x-inference-pod: granite-a-predictor-5895f7b954-9sltf
----

* Praxis alternates between `granite-a` and `granite-b`: round robin across two InferenceServices
* When `granite-b` stopped, its health check failed, Praxis marked it unhealthy and sent everything to `granite-a`
* After the restart, `granite-b` rejoins: its new pod has a new name
* The simulated 429 reached the client unchanged

[NOTE]
====
KServe's predictor Services are headless, so a restarted model gets a new pod IP address behind the same name. Praxis {praxis_version} caches DNS answers for 60 seconds, so for up to a minute after a restart it can still send requests to the old address, and they fail with a 502 or 504. That's why the restart step waits 60 seconds before sending traffic.
====

== Exercise 4: Anthropic clients, OpenAI backends

The simulated models are reached on OpenAI Chat Completions. Praxis AI can serve clients that speak the Anthropic Messages API, such as Claude Code, from those backends.

. Send an Anthropic Messages request:
+
[source,role="execute"]
----
curl -s $AI/v1/messages -H 'content-type: application/json' -H 'anthropic-version: 2023-06-01' \
  -d '{"model":"qwen3-8b","max_tokens":20,"messages":[{"role":"user","content":"hello"}]}'; echo
----

. Send it again as a stream, and list the event types:
+
[source,role="execute"]
----
curl -sN $AI/v1/messages -H 'content-type: application/json' -H 'anthropic-version: 2023-06-01' \
  -d '{"model":"qwen3-8b","max_tokens":5,"stream":true,"messages":[{"role":"user","content":"hello"}]}' \
  | grep '^event' | sort | uniq -c
----

. Ask for extended thinking, which OpenAI Chat Completions can't express:
+
[source,role="execute"]
----
curl -s $AI/v1/messages -H 'content-type: application/json' -H 'anthropic-version: 2023-06-01' \
  -d '{"model":"qwen3-8b","max_tokens":50,"thinking":{"type":"enabled","budget_tokens":20},"messages":[{"role":"user","content":"hi"}]}'; echo
----

=== Verify

Expected output from the first request (trimmed):

----
{"content":[{"type":"text","text":"..."}],"id":"msg_chatcmpl-...","model":"qwen3-8b","role":"assistant","stop_reason":"end_turn","type":"message","usage":{"input_tokens":...
----

Expected output from the stream:

----
   4 event: content_block_delta
   1 event: content_block_start
   1 event: content_block_stop
   1 event: message_delta
   1 event: message_start
   1 event: message_stop
----

Expected output from the thinking request:

----
{"error":{"message":"`thinking` cannot be translated to Chat Completions","type":"invalid_request_error"},"request_id":null,"type":"error"}
----

* The client got an Anthropic-format reply. Its `id` starts with `msg_chatcmpl-`: the backend answered in OpenAI Chat format, and Praxis translated the request, the path (`/v1/messages` to `/v1/chat/completions`) and the response.
* Streaming was translated into Anthropic's event sequence
* Translation is strict: a feature with no equivalent is refused with a 400, not silently dropped

For clients that send such features by default, the `allow_lossy_features` option on the translation filter strips them and reports that it did.

== Exercise 5: Tokens and time to first token

AI cost and capacity are measured in tokens. The `token_count` and `time_to_first_token` filters turn what the backend reports into per-model metrics.

Streaming needs one more piece. An OpenAI-compatible server only reports token usage in a stream if the client asks for it, with `stream_options.include_usage`. Most clients don't, so the gateway's `stream_usage_inject` filter sets it on every streaming chat request. That way streamed tokens are counted no matter which client sent them.

. Generate some streaming traffic for both models:
+
[source,role="execute"]
----
for m in granite-3.1-8b-instruct qwen3-8b; do for i in 1 2 3; do
  curl -sN -o /dev/null $AI/v1/chat/completions -H 'content-type: application/json' \
    -d "{\"model\":\"$m\",\"max_tokens\":30,\"stream\":true,\"messages\":[{\"role\":\"user\",\"content\":\"hi\"}]}"
done; done
----

. Read the AI metrics:
+
[source,role="execute"]
----
oc exec deploy/praxis-ai -- wget -qO- http://127.0.0.1:9902/metrics \
  | grep -E '^praxis_ai_(prompt_tokens_total|output_tokens_total|ttft_seconds_(sum|count))'
----

. In the **OCP Console** tab, go to **Observe** → **Metrics** and run these two queries. Each query box takes one PromQL expression. Paste the first query and click **Run queries**. For each of the others, click **Add query**, paste it into the new box, and run again.
+
Output tokens per second, per model:
+
[source,promql]
----
sum by (model) (rate(praxis_ai_output_tokens_total{namespace="praxis"}[5m]))
----
+
Average time to first token, per model, in seconds:
+
[source,promql]
----
sum by (model) (rate(praxis_ai_ttft_seconds_sum{namespace="praxis"}[5m])) / sum by (model) (rate(praxis_ai_ttft_seconds_count{namespace="praxis"}[5m]))
----

. Open the **Praxis gateways** dashboard you created in Module 2 (**Observe** → **Dashboards (Perses)**, project **praxis**). The **AI gateway** row now shows output tokens per second and time to first token for each model. In the **Traffic** row, "Requests per second, by cluster and backend" shows the `granite` cluster's traffic split across `granite-a-predictor` and `granite-b-predictor`, and the failover from Exercise 2.

=== Verify

Expected output (counts vary):

----
praxis_ai_prompt_tokens_total
{model="granite-3.1-8b-instruct",cluster="granite"} 30
praxis_ai_prompt_tokens_total{model="qwen3-8b",cluster="qwen"} 42
praxis_ai_output_tokens_total{model="qwen3-8b",cluster="qwen"} 62
praxis_ai_output_tokens_total{model="granite-3.1-8b-instruct",cluster="granite"} 89
praxis_ai_ttft_seconds_sum{model="qwen3-8b",cluster="qwen"} 2.7425160180000003
praxis_ai_ttft_seconds_count{model="qwen3-8b",cluster="qwen"} 9
praxis_ai_ttft_seconds_sum{model="granite-3.1-8b-instruct",cluster="granite"} 1.2391847950000001
praxis_ai_ttft_seconds_count{model="granite-3.1-8b-instruct",cluster="granite"} 8
----

* Token counters are labeled by **model** and **cluster**, and include the streamed requests
* Time to first token (sum divided by count) is about 0.15 s for granite and 0.30 s for qwen, matching the latency the simulators were configured with

[NOTE]
====
Praxis AI also has a `token_usage_headers` filter, but it can't add token headers for OpenAI or Anthropic backends. Their usage numbers arrive at the end of the response body, after the response headers are already sent. Use the metrics instead.
====

== Exercise 6: Add a model with zero downtime

Bring a third model online while the gateway keeps serving.

. Serve a simulated `llama-3.1-8b-instruct` as a new InferenceService:
+
[source,role="execute"]
----

EOF

----

. Confirm the gateway doesn't know it yet:
+
[source,role="execute"]
----
chat llama-3.1-8b-instruct -i | head -1
----

. Edit the gateway configuration:
+
[source,role="execute"]
----
oc edit configmap praxis-ai-config
----
+
Add two things:
+
* A route in the `router` filter: `x-model: llama-3.1-8b-instruct` to `cluster: llama`
* A cluster in the `load_balancer` filter named `llama`, with endpoint `llama-predictor.praxis.svc.cluster.local:8000`, and the same host name in `trusted_private_endpoints`

== Troubleshooting

**Issue**: The `praxis-ai` pod crashes with `fatal: unknown filter type`

**Solution**: The configuration names a filter the published image wasn't built with. Experimental filters such as `token_ceiling`, `token_rate_limit` and the OpenAI Responses filters need a custom build or an `-experimental` image.

**Issue**: A new route never takes effect

**Solution**: Check `oc logs deploy/praxis-ai | grep -i reload`. A `reload failed` line explains what was wrong, and the old configuration stays in place. A frequent cause is a route that names a cluster missing from the `load_balancer` filter.

**Issue**: A request fails with 502 or 504 right after a model restarts

**Solution**: The restarted model has a new pod IP address, and Praxis caches DNS answers for 60 seconds. Wait a minute and retry.

**Issue**: `chat: command not found`

**Solution**: The terminal reconnected and lost the helper. Rerun the block in "Deploy the Praxis AI gateway" that defines `AI` and `chat`.
